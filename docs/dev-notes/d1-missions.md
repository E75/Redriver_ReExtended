# Driver 1 missions in the REDRIVER2 engine (plan)

Status 2026-10-13: Part 1 (format research) done, nothing implemented in the engine. Part 1 files are committed on `feature/d1-cars-and-lights` (shared working tree, another session is active there); engine work (Part 3 on) goes to `feature/d1-missions` from `main`. Read `CLAUDE.md` (Driver 1 DLC findings) and `plans/driver1-cities.md` first. Goal: play the Driver 1 story missions (and later the other modes) in the converted D1 cities. Rule: no D1 data in the repo; everything is converted at runtime from the player's own `DRIVER1\` folder.

## 0. Result of the research

- `MISSIONS\MISSION.BLK` (70 772 bytes on the D1 disc) holds ALL missions: a table of 124 `u32` offsets (entry 123 = file end), 123 scripts.
- 0..43 = the 44 story missions (Miami 0-12, San Francisco 13-24, Los Angeles 25-32, New York 33-43). 44..123 = short scripts: cutscene or chase glue (44-59), checkpoint races (60-67, "Hit the checkpoints"), timed runs (68-75, "Out of time!"), pursuit variants (80-87, "Ram him!"), races "Finished!" (106-113), tiny helper scripts without text (76-79, 88-105, 114-123). Their exact use is still unknown (frontend tables).
- Every script is a stream of 32 bit records `[opcode, args...]` without header. All 123 scripts split exactly into records with the length rules below (`d1mission.py --check`: 123 ok, 0 bad). 76 distinct opcodes are used, 65 of them by story missions. About 20 opcodes appear in nearly every story mission.
- The D1 executable (`SLES_018.16`) contains the interpreter. It was decompiled with Ghidra; its main loop (`H_68758`, switch over opcodes 1..0x72) and its prescan are read. Semantics below come from that code, not from guesses, unless marked (?).
- The D1 world coordinates in the scripts equal the coordinates of our converted LEVs (the converter keeps world positions), so start positions and target positions can be used unchanged. To verify per city with `-shot` at the start position (ground height, road under the car).

## 1. File format (verified)

Record length in bytes (`FUN_8006822c`, table at 0x8008b738 in the executable). The table is embedded in `src_rebuild/tools/d1conv/spike/d1mission.py` (`RECLEN`). Special rules: op 2 = 12, or `args[1] + 12` when the variable is a string variable (set `STRING_VARS`); op 22 = `args[1] + 12`; op 20 = `args[0] * 12 + 8`; op 70 = `args[2] + 16`; op 94 = `args[0] + 8`; op 104 = `args[0] * 4 + 8`; op 86 = up to and including the next word `0x7FFFFFFF`.

Text records: op 22 `[time, len, chars...]` (message shown by the HUD: `THE BANK JOB`, `Get to the bank.`) and op 2 on a string variable `[var, len, chars...]` (failure texts, e.g. var 21 = out of time message). Text is zero padded to 4 bytes.

Header records seen at the start of every story mission (prescan, not executed): op 19 `[x, z]` player start position, op 52 `[rot]` start rotation (0..4095 = full turn like D2, sign possible), op 34 `[city]` D1 city id (0 Miami, 1 San Francisco, 3 Los Angeles, 5 New York; 6 and 7 in the "Finished!" scripts, meaning open), op 108 `[n]` mission number 1..44, op 22 `[time, len, name]` the mission title.

## 2. Interpreter model (from the executable)

State: one mission state struct (register s6 in the code), a script pointer (+0x2b8), end pointer (+0x2b4), 72 script variables, 16 byte entries at 0x8008b7ac: `{type, pointer to an engine global, ...}`, type 1 = string, 3 = int. Variables are the bridge to engine state (e.g. var 45 is set 1 at the start of every mission and 0 at the end; var 1 points at the mission timer global 0x97144). One thread runs per frame until a record yields (ops 7, 24, 77/78 wait, 86, 87, 102, 108).

Runtime ops decoded so far (args after the opcode):
- 1 end script. 2 `[var, value]` or string var. 12/14 `[var]` inc/dec, 16/17 `[var, n]` add/sub. 109 `[varA, varB, label]` jump when equal, 106 `[label]` jump, 100 jump to start, 99 restart.
- 7 wait while the state word (+0x104) is non-zero. 24 `[n]` wait n seconds (n x 30 frames). 77/78 start / wait for a "character" action (struct 0xbfba8). 108 wait for the game-over state (mission end).
- 22 show message. 38 `[0..4]` result code (global 0x9719c; 0 at start, 2 on success in `TAKE A CAB`: real meaning to confirm).
- 25 `[radius, x, z]` set up target 0 (destination marker), clears all other target slots. 69 `[slot, radius, x, z]` same for a slot. 26/27 target 0 on/off (counts active targets). 70 `[slot, ...]`, 71 `[slot, a, b, c, d]`, 92/96/97 slot properties (flags, link to a car: `[slot, carIndex|-1|-2]`).
- 8 / 9 `[t]` timer mode (count up / count down from t), 58 clear timer, 59/60 add/subtract time, 28/29 timer bit, 107 split time bookkeeping, 101 best time update.
- 54 `[id, a, b, c, d]` spawn a car (model/colour/x/z, handle stored in +0xf8), 102 wait until the spawn result exists, 113 `[slot, car]` save car state, 114 `[slot]` respawn it, 65 `[n]` set damage limits, 88 snapshot of the player state, 82 `[idx, ...]` give an object a route (4 words), 80 `[idx, a..f]` define a character record, 83, 85, 93, 95, 98, 103, 111, 112: effects/camera/sound/table setters (not read in detail yet).
- 4 and 33 `[slot, a..e]` define a trigger area; the record is followed by code that runs when it fires (the pointer is the end of the record).
- 10/11 set/clear a global flag 0x962cc, 36/37, 55/56, 90/91 set/clear bits of +0x11c, 49/50 clear/set chase flags (globals 0x97134, 0x96a14), 53 `[n]` HEAT_MIN: heat = max(heat, (n-1) x 430 + 659) and remember the player position (heat 0..4096, cops chase from 659; this is exactly D2 felony: `FELONY_PURSUIT_MIN_VALUE` 658, `FELONY_MAX_VALUE` 4096, `felony.h`; so the D2 cop logic needs no new system, map n to `car_data[].felonyRating`), 20 `[n x (a,b,c)]` test a list of positions (spawn clearance, result in +0xf8).

Opcodes only used in the prescan (no runtime effect): 19, 30, 31, 34, 39, 40, 52, 61, 63, 64, 66, 67, 84, 89, 105, 108, 110. Several of these set global tuning values (e.g. 63, 64, 66, 67, 84: byte/word globals at 0x964fc, 0x96b30, ...); to read: 30, 31, 39, 40, 61, 89, 105, 110.

### 2b. Target model (read from `FUN_80069760`, 2026-10-13)

- A target slot (11 words, up to 6 active, `+0x298` counts them) = `{radius, far range, countdown, flags, position pointer}`. Op 25 / 69 set radius = arg 0 and make the far range at least that (defaults: radius 750, far range 24000, slot countdown 450 frames). Position test is the flat 2D distance player to target, the same test as D2 (`Long2DDistance(...) <= point.radius`, `mission.c:2070`), and both games use the same world units, so radius, x and z carry over 1:1. Large radii (30000-120000) are real: they are wide arrival zones (safe house, "lose the tail" areas). D2 has the matching flag `TARGET_FLAG_POINT_STOP_COPS_TRIGGER` / `gStopCops` for a zone where cops give up.
- Script state word = variable 3 (`STATE`): `SETVAR STATE 2` = wait for a target. The target code sets 0x7fff when one slot is reached (the first slot reached wins, the others stay until the script clears them; `WAIT_STATE` then continues and resets the state to 0), 7 when a slot countdown ran out, 0xff0 when the timer reached 0 (mission failed, `FAIL_TEXT` var 5 is shown). Several slots (op 69) therefore mean "reach any of them", mission 7 PAYBACK = any of 5 restaurants.
- Extra arrival rules: `EARLY_LIMIT [t]` with `EARLY_CHECK_ON` = the target only counts once the countdown timer is down to t ("Too Early. Come back later.", THE BANK JOB, 3 missions); `SPEED_GATE` (var 32) = 1 needs speed <= `SPEED_LIMIT` (var 33, 75 or 100) to arrive, i.e. stop in the circle (pickups); `COPS_BLOCK_ARRIVAL` (var 13) = 1 refuses arrival while heat >= 659 and cops are chasing ("lose the tail" before you can finish).
- Checkpoint races (`+0x2d0` = 2): every checkpoint adds 1 second (0x4000) to the timer and increments the checkpoint count.
- Arrival while heat is high adds heat 34 only in the "too early" case; pursuit start is `HEAT_MIN`.
- D2 mapping: reach test = `Target_Point` unchanged; EARLY_LIMIT / SPEED_GATE / COPS_BLOCK_ARRIVAL have no D2 target flag, so they become D2 script conditions (a script word that reads the timer, the player speed, the felony value and branches) in front of the point target. Checked in `mission.c`: the D2 VM has one function (`0x4000020` process target) and four readable/writable variables: `0x2000008` timer (count / 3000 = seconds, so D1 timer / 16384 -> D2 count x 3000 per second), and the cop tuning `gCopDesiredSpeedScale` (0x2000100), `gCopMaxPowerScale` (0x2000101), `gMinimumCops` (0x2000102), `maxCopCars` (0x2000103), which are the D2 twins of the D1 cop tuning variables (42/43/47/48/49). Missing for the arrival rules: player speed and felony/heat. Decision (2026-10-13, replaces the earlier idea of script variables): the three rules become new flags on the Point target, checked in `MRProcessTarget` (`mission.c:2070`) next to the distance test, so the marker stays visible while the rule blocks arrival (a script condition in front of `ProcessTarget` would hide the marker). `TARGET_FLAG_POINT_MAX_SPEED` 0x4000000 (limit in target int 12, compare `FIXEDH(wheel_speed)`) and `TARGET_FLAG_POINT_MIN_TIMER` 0x8000000 (EARLY_LIMIT: D2 timer count in int 13, message offset in int 14, countdown timers only). COPS_BLOCK_ARRIVAL needs NO new flag: D2 already has the rule on the Point target (`point.loseTailMessage != -1` and `copsAreInPursuit` block arrival and show the message, `mission.c:2161`), so the converter just writes the "Lose the tail." text offset into int 8. Flags are set only by D1 missions, so D2 files are untouched. The prototype already writes MAX_SPEED. D1 speed units are assumed equal to the D2 units (both lineages: speed limits 56/97/138, speeding at 1.5x / 120 / 180); this is the one unmeasured assumption, calibrate with `SPEED_UNIT_PERCENT` after the first in-game run.

## 4. How this maps to the D2 engine

D2 has a stack VM (`mission.c HandleMissionThreads`, push/command/operator/function, `MS_MISSION` header, `MS_TARGET` list of point / car / event targets, loose file `MISSIONS\M%d.D2MS` loaded at `mission.c:471`). Take a Ride for D1 cities is already built in code.

Chosen route: translate each D1 script into a D2MS image in the converter (`DRIVER1\CONVERTED\M<n>.D2MS`, bump `D1DLC_CONVERTER_VERSION`), the engine stays D2. A native D1 interpreter in the engine is the fallback for ops D2 cannot express.

Likely mapping (to be proven in Part 3):
- op 19/52/34/108 -> `MS_MISSION` start position, rotation, city, title, number. Title text from op 22, texts from the string variables -> D2 message strings.
- op 25/69 + 26/27 -> `Target_Point` (x, z, radius), completed -> next step of the script.
- op 54 + 97 + 82 -> `Target_Car` (model, colour, position, flags: chase / tail / ram / protect).
- op 8/9/58-60 -> D2 mission timer (`MR_TIMER`), op 38 + 108 -> complete or fail with message.
- ops 24, 7, 2, 109, 106: control flow -> D2 script words (`SetVariable`, `Jump`, `BranchIf`, wait via function calls).
- Pickups (passengers), trigger areas (4/33), characters (80, 77/78), cutscene/camera ops: probably no D2 equivalent as is; D2 events or the in-game cutscene system may cover part of it.

### 4b. D2MS layout the converter must write (read from Chicago mission 1 of `MISSIONS.BLK`, `LoadMission` mission.c:457)

- Header `MS_MISSION` = 33 ints (132 bytes, `dr2types.h:610`): `id` = bytes `SM2D` (`MISSION_IDENT`), `size` = 132 (offset of the target array), `city` (D1 city index 4..7 works: `GameLevel = header city`), `time` (0 day .. 3 night), `weather`, start x / z / rotation, `type`, `timer` (short) + `timerFlags` (short), `strings` (number of script words), cop data (`speed`, `power`, `min`, `max`; 4096 = neutral), message offsets `msgCarWrecked`, `msgOutOfTime`, `msgComplete`, `msgDrowned` (byte offsets into the string block, -1 = none), `region` 0, `route` 0, `playerCarModel`, `playerCarColour`, `maxDamage`, `residentModels[5]`, `nCutscenes`, `title`, `msgPoliceCar`, `msgDoorsLocked`.
- Then exactly 16 `MS_TARGET` (64 bytes each, `MAX_MISSION_TARGETS`), then `strings` script words (u32), then the zero terminated strings back to back. Message arguments in the script are byte offsets into that block.
- Script words: top byte 0x00 / 0x02 / 0xff = push a value (0x02xxxxxx = read variable), 0x01 = command (`0x1000050` ShowPlayerMessage [priority, offset], `0x1000051` PlayCutscene, `0x1000010` SetVariable, `0x1000001` BranchIf [relative jump], `0x1000021` CompleteAllActiveTargets, `0x1001002` StartThreadForPlayer, `0x1001000` StopThread, `0x1000030` SetPlayerFelony), 0x03 = operator, 0x04 = function (`0x4000020` process target [index] -> result). Example (Chicago 1): `push 4; fn ProcessTarget; push -4; BranchIf` is the loop "wait until target 4 is done".
- The file is found as `MISSIONS\M<n>.D2MS` relative to the data folder (`DRIVER2\`), so D1 files in `DRIVER1\CONVERTED\` need a small engine hook (see section 8).

## 5b. Conversion rules (the player supplies the game, we ship no D1 data)

- Input is only the player's own `DRIVER1\MISSIONS\MISSION.BLK` (the player copies the `MISSIONS` folder from their disc or ISO next to `LEVELS` and `DATA`, like today). No executable, no ISO reading needed at runtime. Option for later: read the ISO directly (ISO9660 mode 2), only if copying proves too hard for players.
- The repo holds format knowledge only (record lengths, opcode names, semantics, mapping rules), never a copy of a script, text, coordinate or a file derived from them. Texts and coordinates are read from the player's file at conversion time and written to `DRIVER1\CONVERTED\`.
- Strict conversion, no guessing: a mission is converted only when every record parses, every opcode is `confirmed` in `OPNAMES` and has a mapping, and every variable it uses is mapped. Otherwise the converter logs `mission N skipped: opcode X` and the menu does not offer it. Unconfirmed opcodes are never given a default behaviour.
- Verification layers, each scriptable: (1) `d1mission.py --check` exact parse; (2) `--coverage` lists unconfirmed opcodes; (3) converter self-check: start position and targets lie inside the converted map and on a road or land cell (same style as `D1Conv check`); (4) in-game test per mission with `-d1mission <n>` and `-shot` (position, ground, target marker, end state in the log); (5) D2 cities unchanged (Chicago, Havana, Vegas shots).
- The converter version stamp (`D1DLC_CONVERTER_VERSION`) covers mission output too, so improved rules reconvert automatically.

## 5c. Isolation: D1 missions must never harm the Redriver game (user, 2026-10-13)

- **Separate code:** all converter code in new files (`src_rebuild/d1dlc/d1_missions.cpp/.h`), all menu code in new functions; touching existing files is limited to a few one-line hooks.
- **Every engine hook is gated** by a D1 mission number range (D1 missions use numbers from `D1_MISSION_BASE` 1000 up, D2 never reaches it) or by `IS_DRIVER1_CITY(GameLevel)`. Hooks: (1) `LoadMission` opens `DRIVER1\CONVERTED\M<n>.D2MS` with an explicit path for numbers >= 1000 (like the converted LEV); (2) three new Point target flags in `MRProcessTarget` (max speed, min timer, no cops, see section 2b), no effect on files that do not set them; (3) the menu button and the new built-in screens.
- **Kill switch:** `config.ini [d1dlc] missions=1` (default on while it works, off hides the button and skips mission conversion). A broken release can be turned off without a rebuild.
- **Failure stays local:** mission conversion runs after the city conversion; an error is logged (`mission N skipped: ...`) and never changes the city result, the `.VER` stamp of the city or any file outside `DRIVER1\CONVERTED\M*.D2MS`. A mission file that fails to load returns to the menu, it never starts a half mission.
- **Separate branch and build:** work on `feature/d1-missions` from `main`, built in a clean copy (the shared working tree holds uncommitted work of other sessions). Before every commit: Chicago, Havana and Vegas `-shot` runs unchanged, plus the D1 city shots, as CLAUDE.md requires.

## 7. Design decisions (user, 2026-10-13)

- **Cops and passengers: adapt the D2 logic, do not copy D1.** Cops: D1 chase ops (49/50, 53, vars 47-49, op 51 timing) set the D2 cop/felony state (`SetPlayerFelony`, cop difficulty `CopDiffLevel`, `CARTARGET_FLAG_ISCOP` cars), tuned until the mission plays well in the D2 pursuit system; the D1 cop car (model 0) is the cop car. Passengers (pick up / drop off): D2 has no passenger; a pickup becomes a point target with a message and a "passenger on board" script variable, the drop off a second point target (D2 mission car flags like `CARTARGET_FLAG_SET_PLAYERCAR` and escape/ped events may replace parts later). Goal is a mission that feels right, not the same code path.
- **Mission cars reuse the car types that already exist in a D1 city** (cop car model 0, civilian cars 1 and 2, the 4-5 player cars 8..12). The converter maps each D1 `SPAWN_CAR` model to the nearest of these (cop to cop, taxi/van/civilian to 1 or 2, sports or getaway cars to the player-car pool by class); not 1:1. No new texture pages, so the VRAM slot limit is not touched. The mapping table lives in the converter and is listed per mission in the log.
- **Menu: Story - Driver 1 - city - missions, all open.** `MissionCityScreen` (FEmain.c:2822) gets a "Driver 1" button like the one the Take a Ride city screen already has (FEmain.c ~3560, `Driver1CitySelectScreen` at 3601, screen 41 built in code). It opens a list of the available D1 cities, and each city opens a paged mission list (4 per page like `MissionSelectScreen`, FEmain.c:2592, new built-in screen number 49+ because `PsxScreens[49]` ends at 48) with all missions of that city. Missions are standalone: the player picks any mission, no unlocking, no `gFurthestMission`, no story progress, no cutscene sequence. Mission titles come from the converted files (written by the converter from op 22, so no text is stored in the repo). Cities with no converted mission are hidden. Per city counts: Miami 13 (0-12), San Francisco 12 (13-24), Los Angeles 8 (25-32), New York 11 (33-43).
- Missions start through the existing launch path (`GameType`, `gCurrentMissionNumber`, `LoadMission` -> `MISSIONS\M%d.D2MS`) with D1 mission numbers in their own range (to choose, e.g. 1000 + n) so they never collide with D2 files.

## 9. Chase / ram missions and REPLAY.BLK (research 2026-10-13)

Missions with a target CAR (6, 11, 24, 27, 35, 40 = BEGIN_MISSION 7, 12, 25, 28, 36, 41; also 7, 10, 12, 15, 22, 23, 36): op 61 (CFG_962EC), `TARGET_SLOT` / `SLOT_FLAGS_134` / `SLOT_FLAGS_13C` / `SLOT_VALUES` (identical in every one of them), `SLOT_LINK_CAR [slot, 23]` and `STATE 5` (ram or follow the car) or `STATE 4` (taxi scare).
- `SLOT_FLAGS_13C [0, 65]`: 65 = 0x41 = D2 `CARTARGET_FLAG_RANDOMCHASE | CARTARGET_FLAG_ESCAPE_TARGET`: the D1 target car is a "random chase" like the D2 chases (`TriggerChase`, `gRandomChase` 2..14).
- `REPLAYS\REPLAY.BLK` (1123748 bytes): offset table of 362 u32 (-1 = empty), 18 groups of 20 slots, the first 15 of each group filled (variant 0..14, 215 entries, each 5220 bytes). The group is found through the byte table at file offset 0x7b12c of the D1 EXE (`d1.bin`): BEGIN_MISSION numbers 7, 12, 25, 28, 36, 41 (the six chase missions), 110..117 and 170..173 (other modes), terminated by 255. Loader: `FUN_8005bd6c(missionNumber, variant)` -> entry index = groupIndex * 20 + variant, read into a buffer at 0xd8000 and copied into the chase replay buffer. So every chase mission has 15 recorded runs of the target car, one picked at random like the D2 chases.
- Entry format = the D2 `PADRECORD` stream: 3 byte records `{pad, analogue, run}` starting at byte offset 1 (pad 0x20 / 0x24 / 0x40 / 0x44 are the common ones, run = extra repeats, see `Get` in replays.c). ATTRACT1.R (the attract mode replays of the D1 player) has the same layout. The bytes after the records are leftover memory of the recorder (identical in unrelated groups), NOT a start position. It is an INPUT recording: it only reproduces the drive on the D1 physics from the same start state.
- NOT found yet: where the target car starts (position, direction, model). The scripts hold no spawn for it (`SPAWN_CAR` is only used for parked cars); `SLOT_LINK_CAR [0, 23]` links slot 0 to car index 23 which the chase set-up creates. Probably in the D1 chase set-up code that calls the loader (`FUN_800590a4` -> `FUN_8005bd6c`, all.c), not yet read.
- Consequence: a faithful port needs D1 physics to replay the inputs, which the D2 engine does not have (D2 handling differs and the world scale differs). Adaptation options (user decision needed): A) spawn a D2 car near the player start and drive it with the D2 civilian / lead AI, ram rule = D2 `chasing.maxDamage`; B) replay the D1 inputs on the D2 physics (diverges, probably drives into walls); C) leave the 13 chase missions out.
- D2 pieces that would be used: `Target_Car` type 3 (`MRCreateCar` -> `InitPlayer(.., CONTROL_TYPE_LEAD_AI, ..)`, needs a junction route in the mission header, `LeadValues`, LEAD.BIN) or type 0 with `chasing.maxDamage` (the ram rule, mission.c ~2416).
